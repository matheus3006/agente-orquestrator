P7 — O sistema sabe e não te conta

Quatro defeitos com a mesma assinatura. Juntos, são o que impede você de deixar o orquestrador rodando e ir fazer outra coisa.

Tipo Fatia (lote) Origem Baterias 1 e 1b Estado provado ao vivo Kickoff a escrever

Por que é um lote e não quatro itens

Os quatro têm a mesma forma: o sistema detecta uma condição anômala, toma a decisão correta internamente, e não emite sinal para quem precisa agir. Agrupar não é economia de esforço — é que o critério de aceite é o mesmo para os quatro: "depois do conserto, existe um sinal observável pelo dono, e o teste prova o sinal, não a condição".

O custo real disto para o seu uso

Você aponta o orquestrador para um projeto e sai. Volta em duas horas. Nada aconteceu e nada te avisou. A issue está OPEN, o time está morto, e não há alerta em lugar nenhum. Esse é o cenário que estes quatro defeitos produzem juntos — e é a diferença entre uma ferramenta e uma demo.

Os quatro

1. 🔴 O circuit breaker está armado e mudo

Provado ao vivo na R27-A (B1b.5): o agente 99f27d66 com adapter "claude" (inválido) recebeu 3 wakeups na issue #5 → 3 runs FAILED com "Adapter nao registrado: claude". Resultado observado no banco:

O que se esperavaO que aconteceu
Issue vai a BLOCKEDIssue segue OPEN, intocada
≥1 evento ISSUE_BLOCKED0 eventos
Alerta ao dono0 alertas
Breaker para o par agente×issueArmado, mas mudo

Duas causas distintas, medidas: wakeup manual de raiz fura o WakeupService:87; e para issue sem conversa a notice fail-softa para log.warn em RepeatedFailureNotice:59-63. A pré-checagem que mata o run está em AdapterRunExecutor:145/AdapterRegistry:23, e execute():117 não tem try/catch.

2. 🔴 adapterType inválido cria time natimorto em silêncio

Achado criando um time COM o CEO (R26-A). O CEO propôs "adapterType":"claude" — inválido; os válidos são claude-code/codex/process em AdapterRegistry:20-23. O gate (ApprovalService:347/404) não valida adapterType — só tipoFuncao e UUID.

Resultado: 3 agentes criados, aprovados, e mortos no primeiro run (0.0s). Cria organização morta em silêncio. O workaround foi PATCH manual para claude-code — e aí o time entregou um digest competitivo excelente. O mecanismo funciona; o portão não confere o que passa.

3. 🔴 O materializer sobrescreve o CLAUDE.md que o agente escreveu

Sobrescrita capturada no disco (R27-A / B1b.6, polling ~1s): 41B com sentinel presente → 514B com sentinel ausente (a dieta sobrescreveu no compile) → 555B (o agente re-appendou). O run 2 reportou GREP_INICIAL=0.

Âncora: CompanyMemoryMaterializer:60-68 faz truncate-write; o compile (AdapterRunExecutor:218) roda depois do checkout (:176). Move 0022-A12 de 🎯 para 🔴.

Com projeto real na jogada isto piora: o CLAUDE.md do workspace passa a ser instrução sobre o seu repositório.

4. ⚪ Diagnóstico errado no checkout (N11)

A mensagem "checkout da issue falhou (já em execução por outro run)" aparece também quando a causa é outra (issue fechada, assignee-mismatch). Âncora conferida: AdapterRunExecutor:178 — não :213, que foi erro de citação da R26-A corrigido pela R27-A. Custo baixo, mas é diagnóstico que manda o operador para o lugar errado.

O item 4 do P2 é primo deste lote

Fronteira, para não fazer duas vezes

O P2 item 4 (RunOutcome.failure(MOTIVO) nunca lido; o front apontando para um run fantasma) é exatamente desta família. Ele já está dentro do escopo do P2 — este lote não deve tocá-lo. Se o P2 devolver o item 4, ele cai aqui.

Critério de aceite do lote

  1. Para cada um dos quatro: um sinal observável pelo dono — evento no activity_log, estado de Issue, ou item no feed. log.warn não conta como sinal; foi exatamente o fail-soft que produziu o defeito 1.
  2. O teste prova o sinal, não a condição. Um teste que verifica "o run falhou" já passava antes do conserto. Tem de verificar que o aviso existe.
  3. Controle positivo no mesmo bloco — condição normal não gera o alarme.
  4. Para o defeito 2, a validação tem de ser no gate, não no run. Falhar na criação, não na execução.

Por que este lote vem depois do P6, e não antes

É a única escolha de ordem discutível do plano. O argumento para deixá-lo depois:

  • Nenhum dos quatro destrói trabalho — eles escondem falha. O P2 e o P3 destroem (Issue viva em BLOCKED; entrega descartada), e por isso vêm antes.
  • O P6 vai criar superfície nova de falha silenciosa (push que falha, PR que não abre, worktree que não coleta). Consertar audibilidade antes do P6 e de novo depois é pagar duas vezes.
O contra-argumento, registrado honestamente

Se você pretende deixar o orquestrador rodando sozinho antes do P6 ficar pronto, este lote sobe para antes do P5. A ordem aqui pressupõe que até lá você acompanha as execuções. Se essa premissa mudar, a ordem muda.
