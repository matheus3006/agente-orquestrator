Ciclo de vida da issue, depois

issue criada  → aponta para um project
checkout      → cria worktree em <projeto>/.wt/#N a partir de default_branch
run           → agente trabalha DENTRO do worktree; commits na branch da issue
saída         → push + abre PR
review        → o card mostra o DIFF (não texto)
APPROVE       → merge (ou não — pergunta 2 do P5)
settle        → worktree coletado com `git worktree remove`

Fatiamento provável

Sugestão de corte — a decidir no P5, registrada aqui só para dimensionar:

  1. Projeto no modelo — entidade, migration, CRUD, a Issue apontando. Sem git ainda. Prova: criar projeto pela UI e ver a issue nascer ligada.
  2. Clone base + worktree por issue — o checkout passa a materializar worktree; o settle passa a coletar. Sem push, sem PR. Prova: dois agentes em issues distintas do mesmo projeto, worktrees isolados, ambos coletados.
  3. Branch + commit + push + PR — a credencial entra aqui. Prova: PR aberto num repo real.
  4. Review de diff — o card mostra a mudança; APPROVE decide o merge.

O corte 1→2 é onde mora a maior parte do risco de regressão (mexe em reaper e em Docker); o 3 é onde mora o risco de segurança.

O primeiro projeto de verdade

Recomendação

Quando chegar a hora, não aponte para um projeto que te importa na primeira vez. Aponte para um repo de teste seu, com histórico real mas descartável, e deixe o ciclo completo rodar — inclusive o REJECT, o reopen e a coleta do worktree. A lição da casa é que o caminho que o fixture nunca pisa é onde o bug vive, e este ponto inteiro é caminho novo.

Ligações

  • P4 — pré-requisito de segurança.
  • P8 — depois disto, N4 passa a valer muito mais: uma org que decompõe sobre um repo real é o produto inteiro.
