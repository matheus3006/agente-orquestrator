P2 — Uma chamada derruba uma Issue viva

O produtor do lock e o coletor do lock discordam sobre o que é um lock válido.

O defeito, em uma frase

POST /checkout com o meu próprio run desta issue, já terminal (SUCCEEDED/FAILED/CANCELLED/INTERRUPTED) passa a cerca, passa o tryCheckout, e carimba a Issue com um lock que nomeia um Run sem futuro — que é, pela definição do próprio IssueRepository.findComLockDeRunTerminal, um lock órfão. O LockOrfaoReaper colhe em ≤5 s e a Issue VIVA cai em BLOCKED.

Uma chamada. Com um runId que a própria API publica.

O diagnóstico que orienta a fatia

O coletor exige "lock segurado por Run COM FUTURO". O produtor só exige "run meu e desta issue". São dois invariantes que precisam concordar e são mantidos à mão em lugares diferentes. Consertar o sintoma sem travar a concordância deixa a próxima divergência nascer igual.

O conserto é separar as duas exigências. O helper compartilhado é o nó.
