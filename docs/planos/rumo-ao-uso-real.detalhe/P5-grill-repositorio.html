P5 — O orquestrador não tem código no modelo dele

Não é bug no backlog. É capacidade ausente — e é a que separa "demo" de "eu uso nos meus projetos".

Tipo Grill Slot não ocupa Código zero Forma já decidida pelo dono Kickoff a escrever

É por isso que todo entregável provado até hoje foi documento — pesquisa, digest competitivo, modelagem de elasticidade, .orq/preview/ci-digest.md. Nunca uma mudança de código num repositório. O agente até conseguiria dar git clone na marra (ele tem Bash), mas nada no produto modela isso: sem credencial, sem branch, o review é de texto e não de mudança, e o workspace é apagado no fim.

A forma, já decidida pelo dono (2026-07-27)

Verbatim do requisito

"Criar uma pasta Orquestrador/<empresa> na raiz do usuário, cada empresa ganha sua própria pasta, gerenciada pelo orquestrador" — dito no contexto de passar a usar o orquestrador para desenvolver os projetos reais dele.

Sobre isso o dono fechou três escolhas:

DecisãoEscolhaConsequência direta
Escopo do agenteEscreve código e abre PR Exige credencial, branch por issue, e o review vira review de DIFF, não de texto
Isolamento entre agentesgit worktree por issue Um clone base no disco; worktree por issue embaixo. Mesmo método que o dono já usa nas faixas paralelas deste repo
Projetos por empresaVários ~/Orquestrador/<empresa>/<projeto>/; a Issue passa a apontar para qual projeto
 
~/Orquestrador/<empresa>/<projeto>/          ← clone base, PERMANENTE
~/Orquestrador/<empresa>/<projeto>/.wt/#N/   ← worktree da issue #N, DESCARTÁVEL

O que já existe a favor — não é obra de raiz

  • O default de hoje já é na home: ~/.orquestrador/workspaces, via @Value("${orquestrador.workspace.root:#{systemProperties['user.home']}/.orquestrador/workspaces}") em WorkspaceResolver:33. A mudança é de convenção de nome, não de lugar.
  • Company.slug é único, não-nulo e IMUTÁVEL (não tem setter) ⇒ serve de nome de pasta sem risco de renomear debaixo do sistema.
  • estado_aplicacao: desenvolvimento ⇒ zero migração, zero camada de compatibilidade. Breaking change é livre.

As colisões que o grill tem de resolver

1. O WorkspaceReaper pressupõe um mundo 100% derivado dele

O javadoc é explícito: ele lista o mundo, deriva o caminho esperado a partir do banco, intersecta — "zero parsing de nome, zero estado especular, zero migração (o nome usa UUID encurtado, a inversão nome→banco é impossível)". Um ref fora de toda derivação é órfão: hoje só WARN, nunca deleção cega.

Uma pasta gerenciada mas com coisa do usuário dentro quebra a premissa. Passa a existir WARN permanente para tudo que você puser lá — e qualquer evolução futura que faça órfão ser realmente coletado passa a apontar para o seu projeto. A fronteira tem de ser explícita antes: clone base = PERMANENTE, worktree = DESCARTÁVEL.

2. Worktree não se apaga com rm -rf

Isso deixa metadado stale no repo base. A coleta tem de ser git worktree remove / git worktree prune — e os reapers de hoje fazem remoção de filesystem. É mudança no mecanismo de coleta, não só no caminho.

3. A chave do workspace muda

Hoje é (company, agent, issue). Com worktree-por-issue, o agente sai da chave — o worktree pertence à issue, não a quem a pegou. Isso mexe em três lugares de uma vez:

  • a derivação do WorkspaceReaper;
  • o nome do volume Docker (orq_<c8>_<a8>_<i8>, com segmento de agente);
  • o workspace _agent (agente sem issue), hoje pathFor(company, agent, null).

O workspace de CONVERSA (chaveado por conversationId, ADR-0031) é outro eixo e permanece.

4. Docker não tem pasta de host

O alvo DOCKER usa volume nomeado, não caminho. Worktree é conceito de filesystem LOCAL; sob Docker vira bind-mount — que é o item 12 do roadmap (Paridade Docker), hoje em fail-soft.

Perguntas que o grill tem de responder

  1. Onde mora a credencial de push? O agente precisa lê-la por definição — "esconder do agente" não é opção. A pergunta real é escopo: token por projeto, por empresa, ou um só? E o que impede o agente da empresa A de ler o token da empresa B?
  2. Quem faz o merge? O APPROVE do review dispara, ou fica sempre na mão do dono? A regra vigente do dono é preferir PR sobre push direto. Encaixa no APPROVE/REJECT que já existe (F-ORG-C), mas é decisão.
  3. O review de diff — o card de Review passa a mostrar o quê? Ligação com o achado B1b.3 (o card hoje já não renderiza o comando/porta que tem na mão).
  4. Onde nasce o clone base? Ato do dono na UI, ou o orquestrador clona ao criar o projeto? E se o repo já existe no disco do dono, adota ou clona de novo?
  5. O que acontece com o worktree quando a Issue é reaberta depois de coletado?
  6. Qual o limite que a decisão NÃO vai fechar, nomeado no alcançável.

O que este ponto NÃO fecha

  • Zero código. O produto é decisão numerada D-REPO-1..N, cada uma com racional — é o racional que impede a próxima sessão de reabrir.
  • Não emite o kickoff da implementação (isso é o P6).
  • Não endurece o guard — isso é o P4, que corre em paralelo.

Ligações

  • P2 e P3 — o ciclo de vida do worktree vai amarrar no lock de issue. Desenhar sobre semântica de posse já correta.
  • P1 — a tabela project nasce com FK, exatamente a classe que a suíte não enxerga.
  • P4 — pré-requisito para o primeiro projeto real entrar.
